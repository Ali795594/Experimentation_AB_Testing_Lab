# Experimentation & A/B Testing Intelligence Platform

A development-ready data science project for analyzing e-commerce A/B
tests: data-quality checks tailored to experimentation pitfalls, two-
proportion z-tests, an explicit statistical-vs-practical-significance
framework, cautious segment analysis, and an educational sample-size/power
simulator.

---

## Project Overview

This project analyzes three synthetic A/B tests (a checkout redesign, a CTA
redesign, and a product page redesign) end-to-end: data-quality validation
→ cleaning → EDA → hypothesis testing → segment analysis → an optional
power/sample-size simulator → a self-contained results dashboard.

## Business Problem

- Did a given experiment actually improve conversion, revenue, or AOV — or
  could the observed difference be explained by chance?
- When *is* a statistically significant result actually worth acting on?
- Do results hold up across device, region, and customer type, or are they
  driven by a specific subgroup?
- How many users does a future test need to reliably detect a given effect?

## Why This Problem Matters

Shipping a product change on the strength of a misread A/B test is
expensive in both directions: shipping a change that doesn't actually help
wastes engineering effort, and killing a change that "wasn't significant"
in an underpowered test can throw away a real improvement. A rigorous,
repeatable analysis process protects against both mistakes.

## Dataset

**Synthetic**, generated by `src/generate_data.py` (~113,000 rows across
3 experiments, fixed random seed). Each experiment is deliberately designed
with a different outcome:

| Experiment | Design | Outcome |
|---|---|---|
| `checkout_redesign` | ~9,000 users/arm | Large lift, statistically **and** practically significant |
| `cta_redesign` | ~2,600 vs ~1,760 users (deliberately imbalanced) | No real effect (noise-level difference) |
| `product_page_redesign` | ~45,000 users/arm | Small lift that's statistically significant (huge N) but **not** practically significant |

Includes realistic **duplicate rows**, **contaminated users** (appearing in
both variants of the same experiment), **missing values**, and
**impossible values** (negative revenue, purchases exceeding sessions).

Columns: `experiment_id, user_id, experiment_date, variant, device,
country_or_region, customer_type, sessions, purchases, revenue,
conversion, average_order_value`

> Raw/processed CSVs are **not** committed (see `.gitignore`) — regenerate
> locally with the commands below.

## Data Quality

`src/data_quality.py` checks for: exact duplicate rows, duplicate
(user, variant) pairs, **contaminated users** (appearing in more than one
variant of the same experiment — this breaks the independence assumption
behind a two-proportion z-test), invalid variant labels, impossible values
(negative revenue, purchases exceeding sessions), missing values, and
sample-size imbalance between arms (the `cta_redesign` experiment is
deliberately generated with an imbalanced ~60/40 split to exercise this
check).

## Data Preprocessing

`src/data_cleaning.py`: exact duplicates dropped; **contaminated users are
removed entirely** from their experiment (we cannot know which variant
actually influenced their behavior); rows with impossible values are
dropped (they look like tracking bugs, not simple sign errors, so
"fixing" them would not be defensible); missing `device` /
`country_or_region` labeled `"Unknown"`; converted rows missing `revenue`
are dropped; `average_order_value` is `NaN` for non-purchasers by
construction (not a data-quality issue).

## EDA

`src/eda.py` produces 5 charts: sample size by experiment/variant,
conversion rate by experiment/variant, revenue distribution (converters
only) by experiment/variant, device breakdown, and conversion by customer
type.

## Statistical Testing

`src/ab_test_analysis.py` uses `statsmodels` two-proportion z-tests for
conversion and an independent two-sample t-test for revenue-per-user.

**Null hypothesis (H0):** treatment conversion/revenue = control
conversion/revenue.
**Alternative hypothesis (H1):** treatment != control.

For every experiment we report: control/treatment sample size, control/
treatment rate, absolute and relative difference, a 95% confidence
interval, p-value, effect size (Cohen's h), and — critically — **both** a
statistical-significance verdict **and** a practical-significance verdict
against a documented, adjustable relative-lift threshold. We never say
"treatment won because p < 0.05" without also checking whether the effect
is big enough to matter.

## Segment Analysis

`src/segment_analysis.py` breaks down each experiment by device, region,
and customer type. This analysis is explicitly labeled **exploratory**:
running many segment cuts is a multiple-comparisons problem (some cuts
will look "significant" by chance alone), and several cuts have small
sample sizes. The module flags low-sample segments and prints a warning
about the multiple-comparisons risk rather than silently reporting
per-segment p-values as if they were confirmatory.

## Optional Experiment Simulator

`src/experiment_simulator.py` is a simple, statistically correct,
**script-based** (not a web app) tool for experiment planning:
- `sample_size_table()`: analytic required sample size per arm for a range
  of minimum detectable effects, given a baseline rate, alpha, and power.
- `simulate_power_curve()`: a Monte Carlo simulation showing empirically
  how statistical power grows with sample size for a known true effect —
  a hands-on illustration of why underpowered tests risk false negatives.

## Dashboards

`src/generate_dashboard.py` builds a **single self-contained HTML file**,
`dashboard/ab_testing_dashboard.html`, with four tabbed views (Experiment
Overview, Statistical Results, Segment Analysis, Sample Size / Power).
Just open it in any web browser - no server or internet connection needed.

```bash
python src/generate_dashboard.py
```

Segment views are labeled **exploratory** in the dashboard; see the
multiple-comparisons discussion under "Segment Analysis" above.

## Limitations

- **Synthetic data**: absolute effect sizes are illustrative; the
  methodology transfers, the specific numbers don't.
- Each user is modeled with a single exposure/session in this simplified
  dataset; a real experimentation platform would need to handle multiple
  sessions per user and time-to-convert.
- The practical-significance threshold in `ab_test_analysis.py` is a
  documented, business-configurable assumption, not a statistical fact —
  different businesses would reasonably set it differently.
- No multiple-comparisons correction (e.g. Bonferroni, Benjamini-Hochberg)
  is applied to the segment analysis; those results are explicitly
  exploratory.
- The two-proportion z-test assumes independent observations; the
  contamination check exists specifically because that assumption can be
  violated by users who saw both variants.

## Future Improvements

- Add sequential testing / always-valid p-values for teams that peek at
  results before a test finishes.
- Apply a formal multiple-comparisons correction to the segment analysis
  for teams that want a stricter confirmatory read.
- Model per-user session-level data (multiple exposures, time-to-convert)
  instead of a single-exposure simplification.
- Add Bayesian A/B testing (posterior probability of improvement) as an
  alternative framework alongside the frequentist tests here.

## Interview Questions

1. **Why generate synthetic data with three different outcomes instead of
   one "successful" experiment?** To demonstrate the full decision space a
   real analyst faces: a clear win, a clear non-result, and the trickiest
   case — statistically significant but not practically meaningful.
2. **Walk me through your null and alternative hypotheses.** H0: treatment
   and control have equal conversion (or revenue); H1: they differ. We use
   a two-sided test since we don't assume the direction of the effect in
   advance.
3. **Why a two-proportion z-test for conversion?** Conversion is a binary
   outcome aggregated into a rate; the two-proportion z-test is the
   standard test for comparing two independent proportions at reasonable
   sample sizes.
4. **What is Cohen's h, and why report it alongside the p-value?** An
   effect-size measure for the difference between two proportions; unlike
   a p-value, it doesn't shrink automatically as sample size grows, so it
   gives a sample-size-independent read on how large the effect actually
   is.
5. **Explain the difference between statistical and practical
   significance using your own results.** `product_page_redesign` had a
   p-value well below 0.05 (statistically significant) but a relative lift
   below our practical-significance threshold — the huge sample size made
   even a small, low-impact difference detectable, but the effect isn't
   necessarily worth the cost of shipping the change.
6. **What is user contamination in an A/B test, and why does it matter?**
   A user who is exposed to both variants (e.g. via a caching bug or
   switching devices) — their behavior can't be cleanly attributed to
   either arm, which biases both groups if they're left in.
7. **Why drop contaminated users instead of assigning them to one variant?**
   There's no principled way to know which variant actually drove their
   behavior; guessing would introduce bias rather than remove it.
8. **Why flag the segment analysis as "exploratory"?** Running many
   subgroup tests increases the chance that some appear "significant" by
   chance alone (the multiple-comparisons problem); framing them as
   hypothesis-generating avoids over-claiming from noisy subgroup cuts.
9. **What would you do about a segment that looks significant in this
   exploratory analysis?** Treat it as a hypothesis and run a dedicated,
   pre-registered follow-up test on that segment before concluding
   anything, rather than acting on the exploratory result directly.
10. **What is statistical power, and why does it matter for interpreting a
    "no effect" result?** The probability of correctly detecting a true
    effect of a given size; an underpowered test can produce a "no
    significant difference" result even when a real effect exists, so a
    null result should always be checked against the test's power.
11. **How did you decide how many users an experiment needs?** Using an
    analytic sample-size calculation (`experiment_simulator.py`) based on
    the baseline rate, the minimum effect worth detecting, and target
    alpha/power — and I validated that calculation empirically with a
    Monte Carlo power simulation.
12. **Why use a business-configurable practical-significance threshold
    instead of a universal rule?** The "size of effect worth acting on"
    genuinely depends on the cost of shipping the change and the value of
    the metric to the specific business — there's no one-size-fits-all
    number.
13. **What's a limitation of treating each user as a single exposure?** It
    ignores repeat visits and time-to-convert, which a production
    experimentation platform would need to model (e.g. via survival
    analysis or session-level aggregation).
14. **How would you extend this to a real production setting** (even
    though this project is intentionally development-ready)? Add
    sequential/always-valid testing so results can be checked before a
    test's planned end date without inflating the false-positive rate, and
    automate experiment health checks (contamination, imbalance) as a
    continuous pipeline rather than a one-off script.
15. **What would you tell a stakeholder who says "the p-value was 0.008,
    so we should definitely ship this"?** I'd show them the relative lift
    and the revenue impact alongside the p-value — a low p-value tells you
    the effect is unlikely to be chance, not that the effect is large
    enough to be worth the engineering cost of shipping it.
